# Nutrition module contract (defined before implementation)
Requirements: authenticated adult profile, searchable source-backed foods, logged grams or multiples of a 100 g serving, four meal slots, edit/delete/copy, favorites, reusable meal templates, plans, hydration, weight and activity. Server is authoritative for nutrients and owner scope.
Schema: Food stores per-100 g nutrients and source ID. Meal→MealItem stores quantity and nutrient snapshots. DailyTarget freezes target values on first log for a date. SavedMeal stores validated food references and gram amounts, with optional planned date. Water/weight/activity use user-local dates.
APIs: GET /foods?search=&category=&sort=&page=; GET /foods/categories; POST /foods; GET/POST /meals; PUT/DELETE /meals/{id}; POST /meals/copy; GET/POST /saved-meals; POST /saved-meals/{id}/log; DELETE /saved-meals/{id}; GET/POST /favorites; GET /dashboard?date=; POST /water, /weight, /activity; DELETE /water/{id}; PUT /goals. Private resource lookups include owner ID. Nutrient values are food nutrient × grams/100; no rounding until display. Imported missing nutrients stay null in catalog; aggregate missing values are disclosed as incomplete.
Validation: grams 1–2000 per item; 1–30 items/meal; date within last 365 days and today for actual logs; planned dates up to 90 days ahead; no future weight/water/activity. Empty state uses zero logged amounts, never fabricated progress. Food calories are source values rather than forced 4/4/9 equality.
Tests: known-food scaling, edit/delete recomputation, cross-user denial, custom-food visibility, copy idempotency, date isolation, invalid inputs, persistence after process restart.
